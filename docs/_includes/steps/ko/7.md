## A. 직접 만든 팀 실행하기

1. **Run**을 한 번 누르세요. Start에 저장한 입력값을 사용하며 별도의 입력창은 열리지 않습니다.
2. 실행이 끝날 때까지 기다리세요. Run을 반복해서 누르지 마세요.
3. **Logs(실행 기록)**에서 최신 실행을 선택하고 세 담당자의 **content**를 순서대로 읽으세요.
4. **Trip Planner → content**에서 최종 일정 초안을 확인하세요.

관광 담당이 고른 지역을 식사 담당이 활용했나요? 최종 일정은 두 담당자의 추천을 바탕으로 만들어졌나요? 실제 식당이 아닌 가상 식사 예시라는 점도 확인하세요.

## B. 팀에 새로운 여행 조건 요청하기

**미션: 관광 한 곳, 그 지역에 맞는 식사 후보, 휴식이 있는 일정으로 바꿔보세요.**

먼저 어느 담당자에게 요청할지 생각해보세요. 이번에는 앞의 추천에서 최종 일정을 구성하는 **일정 담당**에게 조건을 전달합니다. 어떤 결과가 바뀌고 어떤 정보는 유지돼야 할까요?

**Trip Planner → Editor → Messages → User** 끝에 아래 문장을 추가하세요. 기존 참조와 System, Start의 입력은 그대로 둡니다.

```text
For this trip, include only one sightseeing activity, one matching fictional meal if available, and one rest break.
```

Run을 한 번 더 누르고 최신 결과를 확인하세요.

- 관광 활동은 한 개인가요?
- 식사 후보는 남겨둔 관광지의 지역과 음식 취향에 맞나요? 없으면 없다고 설명하나요?
- 휴식이 포함돼 있나요?
- 제공되지 않은 장소·시간·가격을 만들어내지 않았나요?

이전 결과가 이미 조건에 맞았다면 변화가 작을 수 있습니다. 전체 팀을 다시 실행하면 앞 담당자의 답변도 달라지므로, 모든 차이가 지시 수정 때문이라고 단정하지 말고 **요청 조건을 따르는지** 확인하세요.

## C. 선택: 결과를 읽기 쉽게 정리하기

시간이 남으면 User는 그대로 두고 **Trip Planner의 System 끝**에 아래 규칙을 추가하세요. 기존 System을 지우지 마세요.

```text
Format the itinerary as a short numbered list. Keep the card IDs, areas, fictional-food labels and Before you go note.
```

다시 실행해 표현 형식이 바뀌는지 확인하세요. **User는 이번 여행의 요청, System은 담당자가 따를 기본 규칙**을 다룹니다. 서로 충돌하는 조건을 넣는 대신 한 번에 하나씩 바꿔봅니다.

## 실제 여행에 활용하기 전

실제 식당·메뉴와 운영시간·가격·이동시간·접근성은 별도로 확인하세요. 같은 지역이라는 표시만으로 가까운 거리나 편리한 이동이 보장되지는 않습니다.
